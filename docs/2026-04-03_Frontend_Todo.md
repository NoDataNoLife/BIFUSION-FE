# BIFUSION 프론트엔드 미해결 과제(TODO) 및 아키텍처 개선 방향

이 문서는 프론트엔드 개발 중 발견된 기술적 부채(해결해야 할 숙제)와, 앞으로 프론트엔드 구조를 더 튼튼하게 만들기 위한 고민을 담고 있습니다.

## 1. 하드코딩된 가짜 데이터 걷어내기

초기 화면 기획을 위해 컴포넌트 곳곳에 작성해둔 가짜 데이터(Mock Data)들이 남아있습니다.

### 💡 왜 문제인가요?
예를 들어 `ProfilePage`에 '조현희'라는 이름이 하드코딩(코드에 직접 타이핑)되어 있다면, 어떤 유저가 로그인하든 무조건 '조현희'로 보이게 됩니다.

### 🛠️ 해결 방향
* **Zustand 스토어 연동**: 모든 컴포넌트에서 하드코딩된 문자열을 지우고, `const { user } = useAuthStore()`를 통해 진짜 데이터를 불러오도록 전면 교체해야 합니다.
* **로딩 스피너**: 데이터를 서버에서 받아오는 그 짧은 시간(0.5초) 동안 빈 화면이 뜨지 않도록 Skeleton(뼈대) UI나 로딩 스피너를 달아야 합니다.

## 2. API 폴더 분리 (모듈화)

현재 Axios를 통한 백엔드 호출 코드가 `Zustand` 스토어 내부나 컴포넌트 내부에 마구잡이로 섞여 있습니다.

### 💡 왜 문제인가요?
백엔드 주소가 `/api/v1/projects`에서 `/api/v2/projects`로 바뀌면, 프로젝트 전체 코드를 뒤져서 일일이 수정해야 합니다.

### 🛠️ 해결 방향 (API 분리)
`src/api/` 폴더를 새로 만들고 역할별로 파일을 쪼개야 합니다.
* `auth.api.ts` (로그인, 회원가입 관련)
* `project.api.ts` (프로젝트 관련)

```typescript
// src/api/project.api.ts (이렇게 깔끔하게 분리!)
export const getMyProjects = () => api.get('/projects/me');
export const createProject = (data) => api.post('/projects', data);
```
이렇게 하면 백엔드 주소가 바뀌어도 이 파일 하나만 수정하면 끝납니다!

---

## 3. 에러 처리 공통화 (Global Error Handler)

현재는 API 요청이 실패하면 각 컴포넌트에서 개별적으로 `alert('에러가 발생했습니다')`를 띄우고 있습니다.

### 🛠️ 해결 방향
Axios Interceptor를 사용하여, **"백엔드에서 500번대 에러가 날아오면 무조건 빨간색 토스트(Toast) 팝업을 예쁘게 띄워라!"** 라는 공통 규칙을 만들어야 합니다. 이렇게 하면 프론트엔드 개발자가 매번 에러 처리 코드를 짜는 수고를 덜 수 있습니다.
