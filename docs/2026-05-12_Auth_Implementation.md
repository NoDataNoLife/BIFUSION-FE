# BIFUSION 프론트엔드 인증(Auth) 아키텍처 가이드

이 문서는 구글 소셜 로그인부터 접근 제어(보호된 라우트), 그리고 토큰 갱신까지 BIFUSION 프로젝트의 인증 시스템이 어떻게 동작하는지 코드 흐름을 따라 설명합니다. 

---

## 1. 로그인 흐름 (OAuth2 Flow)

사용자가 '구글 로그인'을 클릭했을 때부터 프론트엔드가 화면을 띄우기까지의 전체 과정입니다.

1. **로그인 버튼 클릭**: 프론트엔드는 백엔드의 소셜 로그인 엔드포인트(`http://localhost:8080/oauth2/authorization/google`)로 사용자를 이동시킵니다.
2. **구글 로그인 완료**: 구글에서 인증이 끝나면, 백엔드는 처리 결과를 묶어서 프론트엔드의 특정 주소(`/login/success`)로 다시 돌려보냅니다(Redirect).
3. **토큰 발급**: 백엔드는 이때 사용자 브라우저에 해킹으로부터 안전한 `httpOnly` 방식의 쿠키(Cookie) 형태로 JWT 토큰을 꽂아줍니다.
4. **프론트엔드 후처리 (`OAuth2RedirectHandler.tsx`)**: `/login/success` 페이지 컴포넌트가 로드되면서, 즉시 백엔드에 "내 유저 정보 좀 줘!" 라고 요청(`GET /api/v1/users/me`)합니다. 쿠키가 자동으로 딸려가므로 서버는 정상적으로 정보를 응답합니다.
5. **로그인 완료**: 받아온 유저 정보를 Zustand 전역 저장소(`useAuthStore`)에 저장하고 대시보드로 이동시킵니다.

---

## 2. 권한에 따른 라우팅 제어 (접근 통제)

### `ProtectedRoute.tsx`의 2단계 방어막

로그인하지 않은 사용자가 대시보드에 접근하거나, 필수 정보(닉네임 등)를 입력하지 않은 유저가 서비스를 이용하는 것을 막아야 합니다.

*   **1단계 (인증 체크)**: `user` 정보가 없으면 아예 로그인 화면(`/`)으로 돌려보냅니다.
*   **2단계 (온보딩 체크)**: `user` 정보는 있지만 `user.nickname`이 없다면, 회원가입 마무리 단계인 `/onboarding` 페이지로 강제 이동시킵니다.

이 방어막 컴포넌트를 `App.tsx`에서 대시보드 관련 라우트들 바깥에 감싸주면 보안이 완벽해집니다.

---

## 3. 토큰 자동 갱신 (Silent Refresh)

JWT 토큰 중 '액세스 토큰(Access Token)'은 보안을 위해 수명이 아주 짧게(예: 30분) 설정됩니다. 토큰이 만료될 때마다 유저를 로그아웃시키면 사용성이 매우 떨어집니다.

이를 방지하기 위해 **프론트엔드에서 유저 몰래 토큰을 새 것으로 갱신받는 기술**을 적용했습니다.

### 💡 어떻게 동작하나요? (`src/lib/axios.ts`)
모든 API 요청을 중간에 가로채는 '인터셉터(Interceptor)'를 사용합니다.

1. 프론트엔드가 서버에 뭔가 요청을 보냈는데, 서버가 "너 토큰 만료됐어!" 라며 **401 (Unauthorized) 에러**를 뱉습니다.
2. 에러를 화면에 띄우기 전에 인터셉터가 이 401 에러를 낚아챕니다.
3. 인터셉터는 유저 몰래 백엔드의 **토큰 갱신 API (`/auth/refresh`)**를 찔러서 새로운 토큰이 담긴 쿠키를 발급받습니다.
4. 성공적으로 발급받으면, 아까 실패했던 원래 요청을 다시 조용히 보냅니다.
5. 유저는 아무런 에러를 느끼지 못하고 부드럽게 서비스를 이용할 수 있습니다!

---

## 4. 자주 발생하는 에러 상황 정리

*   **500 에러 (Internal Server Error)**: 백엔드 서버가 죽었거나 뻗은 경우입니다. 프론트엔드 잘못이 아닐 확률이 높습니다.
*   **404 에러 (Not Found)**: 주소가 잘못되었습니다. Axios 기본 주소(`/api/v1`)가 중복해서 들어가진 않았는지 확인하세요.
*   **로그아웃했는데 자꾸 로그인될 때**: 브라우저에 쿠키(토큰)가 찌꺼기로 남아있기 때문입니다. 개발자 도구(F12)의 Application 탭에서 Cookies를 강제로 지워주면 해결됩니다.
