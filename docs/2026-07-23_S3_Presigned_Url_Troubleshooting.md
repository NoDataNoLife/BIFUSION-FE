# BIFUSION S3 Presigned URL 엑스박스(깨짐) 해결 일지

이 문서는 프로필 사진 등 AWS S3 이미지를 불러올 때 이미지가 엑스박스로 깨지는 현상의 원인과 이를 해결한 프론트엔드의 구체적인 방어 로직을 설명합니다. 웹에서 외부 이미지를 다룰 때 꼭 알아야 할 인코딩/디코딩 지식을 배울 수 있습니다.

---

## 1. 🚨 문제 현상: 이미지가 왜 깨지지?

백엔드에서 이미지 주소를 `Presigned URL` 방식(시간제한이 있는 보안 URL)으로 내려주기 시작한 직후, 화면 구석구석에서 프로필 이미지가 엑스박스 네모로 깨지기 시작했습니다. 브라우저 콘솔을 열어보니 `403 Forbidden`(접근 거부) 에러가 잔뜩 떠 있었습니다.

---

## 2. 🔍 범인은 프론트엔드의 `safeEncodeUrl` 함수!

프론트엔드 코드 어딘가에 한글 파일명이나 특수문자가 들어간 이미지가 깨지는 걸 막기 위해 만들어둔 `safeEncodeUrl`이라는 유틸리티 함수가 있었습니다. 모든 이미지는 이 함수를 거쳐서 화면에 렌더링되게 짜여 있었습니다.

### 💡 AWS Signature의 훼손
Presigned URL 안에는 `&X-Amz-Signature=qWeRtY+123%3D` 처럼 AWS가 정교하게 암호화해 둔 아주 길고 복잡한 비밀번호 문자열이 들어있습니다.

문제는 프론트엔드의 `safeEncodeUrl` 함수가 이 주소를 넘겨받으면서 발생했습니다.
1. "이거 내가 한 번 더 안전하게 인코딩(글자 변환) 해줄게!" 하면서 `decodeURI`와 `encodeURI`를 돌려버림.
2. 이 과정에서 비밀번호 문자열에 섞여 있던 `+`나 `=` 같은 기호들이 미세하게 다른 글자로 변환됨.
3. 훼손된 주소를 들고 AWS에 찾아가니, AWS는 **"비밀번호가 틀렸잖아! 해커 녀석!"** 이라며 403 에러를 뱉고 이미지를 주지 않았던 것입니다.

---

## 3. 🛠️ 해결 방안: "비밀번호가 있는 URL은 건드리지 마!"

해결책은 아주 간단했습니다. 들어오는 이미지 주소에 AWS의 비밀번호(`X-Amz-Signature`)가 들어있다면, 프론트엔드가 쓸데없이 가공하지 말고 **받은 순정 상태 그대로 브라우저에 꽂아주도록 예외 처리(Bypass)**를 추가했습니다.

**[실제 수정된 `safeEncodeUrl` 코드]**
```typescript
const safeEncodeUrl = (url?: string): string => {
  // 주소가 아예 안 넘어왔으면 빈 문자열 리턴
  if (!url) return '';
  
  // 핵심 방어 로직 추가!!!
  // 만약 주소 안에 'X-Amz-Signature'라는 단어가 포함되어 있다면?
  // -> 백엔드가 준 Presigned URL이므로 인코딩/디코딩 하지 말고 그대로 내보낸다!
  if (url.includes('X-Amz-Signature')) {
    return url;
  }

  // 그 외의 평범한 주소들만 기존처럼 변환 처리를 해준다.
  try {
    const decoded = decodeURI(url);
    return encodeURI(decoded);
  } catch (e) {
    return url;
  }
};
```

---

## 4. 💡 오늘의 교훈

1. **지나친 친절은 독이 됩니다**: 프론트엔드에서 데이터를 안전하게 하겠다고 무조건 필터(인코딩 등)를 씌우는 것은 외부 서비스(AWS 등)와의 통신에서 예기치 못한 버그를 만들 수 있습니다.
2. **403 에러는 권한 문제**: 프론트엔드에서 이미지가 403으로 깨진다면, 십중팔구 서버나 클라우드(S3)에 넘겨주는 '토큰'이나 '서명(Signature)'이 변조되었거나 누락된 것입니다. 주소창을 복사해서 메모장에 붙여놓고 원본과 글자 하나하나 비교해보는 것이 가장 빠른 디버깅 방법입니다!
