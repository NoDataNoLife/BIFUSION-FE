## 1. 회의에서 먼저 결정할 5가지

1. **버전:** 어느 FE·BE·ML 코드가 실제 서버에서 실행 중인가?
2. **배포:** 최신 Medfusion을 사용할 것인가? 외부 코드와 모델 파일은 누가 준비하는가?
3. **파일 전달:** 증강 파일을 학습 워커가, 학습 모델을 분류 워커가 어떻게 읽는가?
4. **담당·기한:** BE의 AI 연결과 FE의 규격 수정은 누가 언제까지 하는가?
5. **완료 기준:** 저장 후 새로고침, 실패 표시, 실제 결과 파일 확인까지 시험할 것인가?

**오늘 필요한 결과물:** 담당자·기한·다음 회의에 가져올 확인 증거가 적힌 목록입니다.

### 회의 시작 때 읽을 말

> 일반 기능의 API 요청과 AI 화면은 많이 준비했습니다. 다만 실제 서버 연결과 예시 화면이 섞여 있습니다. 핵심 AI는 BE 연결, ML 파일 전달, 배포 준비를 함께 완성해야 하고, 검수 요청도 서버 규격과 맞춰야 합니다. 오늘은 사용할 버전과 저장 방식, 연결 담당·기한부터 정하고 싶습니다.

## 2. 프로젝트를 이해하는 데 필요한 구조

| 이름 | 역할 |
|---|---|
| **FE · 프론트엔드** | 사용자가 보는 화면과 버튼 |
| **BE · 백엔드** | 로그인, 권한, 프로젝트, 게시물, 작업 기록 |
| **ML 서버** | 이미지 생성과 모델 학습·분류 계산 |
| **워커** | ML 서버 뒤에서 실제 계산을 실행하는 프로그램 |
| **DB** | 계정·게시물·작업 기록을 보관하는 곳 |
| **S3** | 이미지·모델 같은 파일을 보관하는 창고 |

**API**는 화면과 서버 사이의 통신 약속입니다. 주소, 요청 방식, 데이터 항목 이름이 맞아야 동작합니다.

### AI의 정상 흐름

1. **입력:** 사용자가 선택한 실제 이미지를 전달합니다.
2. **접수:** BE가 권한을 확인하고 작업 기록을 만든 뒤 ML에 요청합니다.
3. **증강:** 소량의 원본으로 추가 이미지를 만들고 `dataset_id`를 받습니다.
4. **학습:** 그 데이터셋으로 모델을 학습하고 `model_id`를 받습니다.
5. **분류:** 그 모델에 새 이미지를 넣어 정상·비정상 결과를 받습니다.
6. **보관:** 최종 상태와 파일 위치를 저장해 새로고침 후에도 조회합니다.

`dataset_id`는 만들어진 데이터 묶음의 식별자, `model_id`는 학습 모델의 식별자입니다. 단계를 넘길 때 실제 파일과 이 번호가 함께 이어져야 합니다.

**현재 끊긴 구간:** 실제 이미지 전달, BE의 AI 접수·상태·기록 연결, ML 워커 사이의 결과 파일 전달입니다.

## 5. 중요한 문제 5개

### 문제 1 · AI 요청이 실패해도 예시 성공으로 넘어갑니다

**현재 동작**

FE가 작업 생성을 요청하지만 기준 BE에는 그 접수 API가 없습니다. 오류가 나면 FE가 임시 작업 번호를 만들고 진행률을 임의로 올린 뒤 고정 결과를 보여줄 수 있습니다.

파일을 선택해도 해당 요청에는 이미지 내용 대신 **장수만** 들어갑니다. 캐시는 브라우저 메모리 안에 있어 새로고침하면 사라집니다. 취소 요청 실패도 무시합니다.

**왜 중요한가**

진행 화면이나 94.2% 같은 값이 보인다고 실제 AI 계산이 끝난 것은 아닙니다.

**다음 작업 · FE + BE + ML**

실제 이미지·작업·결과를 연결하고, 서버 실패와 시연 실행을 구분합니다. 진행률 100이 아니라 최종 성공 상태로 완료를 판단합니다.

---

### 문제 2 · 워커 사이에 결과 파일을 전달하는 연결이 없습니다

**현재 동작**

증강·학습·분류 워커는 별도 컨테이너에서 실행됩니다. 컨테이너는 프로그램의 실행 공간이며, 같은 서버에서도 파일을 자동으로 공유하지 않습니다.

기본 결과 폴더 `storage`와 학습 임시 폴더 `/tmp/models`가 워커 사이의 공통 폴더로 연결되지 않았습니다. 학습·분류는 로컬 파일을 찾으며 S3에서 이전 결과를 받는 연결도 없습니다.

**왜 중요한가**

> 증강 담당이 자기 방에 파일을 저장했는데, 학습 담당은 자기 방에서 그 파일을 찾는 상황입니다.

각 계산 함수가 정상이어도 다음 단계에서 파일을 못 찾을 수 있습니다. 최신 ML은 이때 가짜 데이터로 대신하지 않고 실패합니다.

**다음 작업 · ML + 배포 + BE**

공유 폴더를 사용할지, S3에 저장하고 다음 워커가 다운로드할지 확정합니다. S3 저장 설정만 켜는 것으로는 충분하지 않습니다.

### 문제 3 · 전문가 검수의 요청 약속이 다릅니다

주소 앞의 공통 `/api/v1`은 아래에서 생략했습니다.

| 기능 | FE가 보내는 것 | BE가 받는 것 |
|---|---|---|
| 전문가 인증 · 이번 수정 | `/experts/me` | `/experts/me` |
| 승인·반려 방식 | POST | PATCH |
| 판정 의견 항목 | `finalComment` / `rejectionReason` | `expertComment` |
| 신청 대상 | RECIPE / DATASET | AUGMENTED_DATA |
| 신청 포인트 | `reward` | `rewardPoints` |

POST·PATCH는 요청 방식 이름입니다. 서버가 정한 방식과 다르면 처리되지 않습니다.

현재 검수는 **본인 소유 증강 데이터**만 지원합니다. 대상 문자열만 바꾸면 되는 문제가 아닙니다. 실제 증강 설정 번호와 검수 작업 번호를 받아야 합니다.

또 표시 문자열 `REV-001`에서 숫자를 뽑아 DB 번호로 사용하고 있습니다. BE가 실제 번호를 제공하고 FE가 그 번호를 사용하도록 맞춰야 합니다.

**다음 작업 · FE + BE**

신청 대상·실제 ID·요청 방식·응답 이름을 맞추고 신청 → 시작 → 임시 저장 → 판정 → 결과 재조회를 시험합니다.

### 문제 4 · 화면 설정 일부가 계산에 적용되지 않습니다

| 설정 | 최신 ML의 사용 여부 |
|---|---|
| 증강 이미지 생성 수·seed | 생성 함수에 전달 |
| 증강 Sampling Steps·Guidance Scale·model_name | 요청 형식에 있지만 증강 계산에는 미전달 |
| 학습 dataset_id·K-shot·epochs | 실제 학습에 사용 |
| 학습 Query 이미지·정답 포함 여부 | 학습 워커 미사용 |
| 분류 model_id·images_base64 | 실제 분류에 사용 |

**설정 용어:** seed는 무작위 계산의 시작값, Sampling Steps는 생성 반복 횟수, Guidance Scale은 생성 방향을 유도하는 강도입니다. epochs는 학습 반복 횟수이며 model_name은 모델 선택 이름입니다.

Query는 별도 평가용 이미지입니다. FE는 이를 선택하게 하지만 실제 이미지 대신 장수만 보내며, ML도 사용하지 않습니다.

**다음 작업 · FE + ML**

설정값을 실제 계산에 연결할지, 화면·명세에서 지원 범위를 줄일지 정합니다. 단독 생성 모드에서는 sampling_steps를 전달하므로 모든 생성 API에서 미사용이라는 뜻은 아닙니다.

### 문제 5 · ‘API 있음’과 ‘정상 운영 확인’을 구분해야 합니다

- `health=ok`: 웹 서버 응답 확인입니다. 워커·GPU·파일 연결까지 점검하지 않습니다.
- API 모의 테스트: 실제 작업 대신 가짜 접수 번호로 시험합니다.
- 3단계 함수 테스트: 같은 프로그램 안에서 계산 함수를 실행합니다. 별도 컨테이너 파일 공유나 FE→BE→ML 연결을 증명하지 않습니다.
- 문서의 96.5% 같은 숫자: 예시이며 프로젝트 실험 성적을 증명하지 않습니다.
- FE 타입 검사 결과와 이번 수정 전후 비교는 [수정·검증 상세](//wsl.localhost/Ubuntu-24.04/home/ysb/projects/BIFUSION/BIFUSION-FE/docs/2026-10-09_Quickfix_Followup.md)에 기록했습니다. 기존 오류 전체 해결과 구분해야 합니다.

## 6. ML에서 개선된 내용과 아직 남은 요구

### 최신 Medfusion 브랜치에서 개선된 것

- DDPM에서 Medfusion으로 이미지 생성 엔진 변경
- 업로드 이미지에 맞춘 짧은 추가 학습 후 변형본 생성
- 데이터셋·모델·유효 이미지가 없을 때 주요 가짜 대체 대신 실패 처리
- ProtoNet에서 K-shot을 사용한 학습과 내부 검증 분할 적용

**Medfusion**은 생성 엔진 이름입니다. **ProtoNet**은 정상·비정상 대표 특징을 만들어 새 사진을 분류하는 모델입니다. **K-shot**은 각 종류의 대표 예시를 몇 장 쓰는지입니다.

출력은 NORMAL/ANOMALY 두 클래스입니다. 화면 예시의 폐렴·심장질환 등 이름을 실제 구현된 질병 진단 기능으로 받아들이면 안 됩니다.

### 배포에 필요한 것

- 사용할 ML 커밋과 외부 `bifusion` 코드 버전
- `medical_diffusion` 소스와 diffusion/VAE 모델 파일 두 개
- 실제 서버 경로·GPU·저장소 설정
- 생성·학습·분류의 채널 설정 일치 — 최신 기본값은 RGB 3채널

모델 가중치는 학습한 숫자를 저장한 파일입니다. VAE는 이미지를 작은 내부 표현으로 압축·복원하는 모델입니다. 파일 존재만으로 유효한 학습 모델임을 증명하지는 않습니다.

### MIGRATION.md도 함께 읽었습니다

검토한 문서는 **origin/Medfusion · `f473b60`의 MIGRATION.md**, 마지막 개정일은 **10월 2일**입니다.

- **“API 계약 변경 없음”**은 ML의 기존 주소·요청 형식을 유지했다는 뜻입니다. FE가 가정하는 BE 주소까지 구현됐다는 뜻은 아닙니다.
- **실패 상태:** 문서 예시는 `FAILURE`지만 실제 외부 응답은 `FAILED`입니다. FE는 실제 응답을 기준으로 오류 이유를 표시해야 합니다.
- **동시 실행:** 워커마다 `concurrency=1`이어도 증강·학습·분류가 각각 하나씩 동시에 실행될 수 있습니다. GPU 전체에 대한 제한은 따로 필요합니다.
- **파일 경로:** 문서의 “리눅스 컨테이너면 OK”만으로는 부족합니다. 별도 워커가 `/tmp/models`를 공유해야 이전 모델을 읽을 수 있습니다.
- **성능·품질:** 문서에 기록된 4090 실행 시간과 이미지 복원 수치는 팀원 측 측정 설명입니다. 이번 조사에서 운영 환경 성능이나 새 의료 영상에 대한 품질을 재현 검증한 것은 아닙니다.

## 8. API 명세에서 고칠 핵심

사진의 그룹 집계는 91개입니다. 읽을 수 있는 **84개만 대조**했고 데이터증강 1개·마이페이지 6개는 행 내용이 없어 판정하지 않았습니다.

### 주소·방식 정정

- 데이터셋: `/datasets`, 수정은 `/datasets/{id}/upload`
- 내 자산: `/assets/datasets`, `/assets/recipes`
- 레시피·후기: `/community/recipes` 계열
- 검수: `/inspections` 계열
- 파일 다운로드: `/files/{fileId}/download`
- 멤버 삭제: PUT → DELETE
- 알림 단건 삭제: `/notifications/{id}` → `/notifications?notificationId=...`

레시피 Fork 기반 새 글 등록은 PUT이 아니라 POST `/community/recipes`에 `forkedFromId`를 넣는 방식입니다.

### 상태 표시 정정

알림·모집·마이페이지·레시피 등 일부는 ‘시작 전’보다 진행됐습니다. 반대로 사용자 이메일 검색은 ‘완료’ 표시와 달리 화면에서 API를 사용하지 않습니다.

**화면 연결 / 규격 불일치 / 예시 / 실서버 검증**을 구분하고, 실제 검증 날짜·결과를 별도 열에 적는 것이 좋습니다.
