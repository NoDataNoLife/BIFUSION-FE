# 백엔드 요청서 — 무엇을 왜 연결해야 하는가?

기준: 2026-10-12. 아래 API 주소 중 **‘제안’이라고 적은 것은 새로 합의할 주소**다. 이미 구현된 것으로 읽지 않는다.

먼저 [전체 구조 그림](ARCHITECTURE.md)을 보고 이 문서를 읽으면 쉽다. 목표는 **실제 이미지로 증강 → 학습 → 추론을 끝내고, 화면을 새로고침해도 결과를 다시 보는 것**이다.

## 1. 팀에 먼저 전달할 메시지

> 최신 ML 코드에는 증강·학습·추론 API와 새 설정들이 있습니다. FE와 BE에는 이전 설정과 모의 작업이 남아 있어, 실행 API의 주소뿐 아니라 실제 파일 전달·작업 번호·결과 저장을 함께 맞춰야 합니다.
>
> 우선 한 프로젝트에서 실제 원본으로 증강하고, 그 결과로 학습하고, 학습된 모델로 새 이미지를 분류하는 최소 흐름부터 연결하고 싶습니다. 진행률 바는 제거하되 대기·실행·성공·실패 상태는 유지하겠습니다.

**API**는 서버끼리 요청하고 답을 받는 통로다. **Job**은 실행한 작업 한 건이다. **DTO**는 요청·응답에 어떤 이름과 형식의 값을 담을지 정한 틀이다.

예를 들어 화면에서 “생성 단계 50”을 선택하면 ML이 이해하는 `steps: 50`을 보내야 한다. 주소가 맞아도 이름이 틀리면 설정이 적용되지 않을 수 있다.

## 2. 요청할 여섯 가지

| 요청 | 왜 필요한가? | 완료 확인 |
|---|---|---|
| 실제 이미지 전달 | 장수만으로는 ML이 계산할 이미지가 없음 | 선택한 파일이 ML 입력으로 전달됨 |
| 최신 DTO·레시피 저장 | 예전 이름의 설정은 무시될 수 있음 | 선택한 값과 실제 실행값이 일치 |
| BE·ML 작업 번호 연결 | 새로고침 후 올바른 계산을 찾아야 함 | 같은 Job의 상태를 다시 조회 |
| 결과 파일과 오류 저장 | 화면의 예시 결과를 실제 결과로 바꿔야 함 | 성공 결과·실패 이유가 재조회됨 |
| 파일 권한·다운로드·삭제 | 다른 사람 파일을 사용하거나 삭제하면 안 됨 | 소유권 확인과 실제 파일 삭제 |
| 개미·용량 확인과 정산 | 중복 차감과 저장 공간 초과를 막아야 함 | 실행 기록·잔액·용량 기록이 일치 |

## 3. API는 이렇게 합의하면 된다

**POST**는 새 작업 생성, **GET**은 조회, **DELETE**는 삭제 요청에 쓰는 통신 방식이다.

| 기능 | 기존 또는 제안 주소 | 주고받을 정보 |
|---|---|---|
| 파일 업로드 | 기존 POST /api/v1/files/temp 재사용 검토 | 파일 자체를 보내고 파일 ID 받기 |
| 증강 시작 | 제안 POST /api/v1/projects/{projectId}/jobs/augment | 정상·비정상 파일 ID와 생성 설정 |
| 학습 시작 | 제안 POST /api/v1/projects/{projectId}/jobs/train | 증강 데이터 ID와 학습 설정 |
| 추론 시작 | 제안 POST /api/v1/projects/{projectId}/jobs/inference | 학습 모델 ID와 새 이미지 파일 ID |
| 작업 목록 | 제안 GET /api/v1/projects/{projectId}/jobs | 프로젝트의 실제 Job 목록 |
| 작업 상세 | 제안 GET /api/v1/projects/{projectId}/jobs/{jobId} | 상태·실제 설정·결과·실패 이유 |
| 작업 삭제 | 제안 DELETE /api/v1/projects/{projectId}/jobs/{jobId} | 연결된 파일의 삭제와 용량 정산 |

`{projectId}` 같은 표시는 실제 프로젝트 번호가 들어갈 자리다.

FE가 현재 쓰는 일반 POST /jobs를 유지하고 `type`으로 증강·학습·추론을 구분하는 방법도 가능하다. 중요한 것은 위 주소 그대로 구현하는 것이 아니라 **FE와 BE가 한 형식으로 합의하는 것**이다.

조사한 JobController에는 댓글 API가 확인됐고 AI 작업 실행·조회 연결이 필요하다. 기존 명세의 주소만 보고 이미 완성됐다고 판단하지 않는다.

### 이미지가 넘어가는 방법

권장하는 추가 설계는 아래 순서다.

1. FE가 원본을 BE 파일 업로드 API에 보낸다.
2. BE가 파일 내용을 확인하고 `fileId`를 반환한다. fileId는 서버에 보관된 파일의 번호다.
3. FE가 증강 요청에 정상/비정상 fileId 목록을 보낸다.
4. BE가 사용자 소유 파일인지 확인하고 파일을 읽는다.
5. BE가 실제 ML 입력인 Base64 문자열 배열로 변환해 전달한다.

**Base64**는 파일을 문자열로 표현하는 방식이다. 현재 ML은 fileId를 직접 받지 않는다. 따라서 4~5번 변환이 필요하다. 저장소 키나 단기 URL을 ML로 직접 넘기는 방식은 ML도 함께 수정하는 후속 계약이다.

## 4. 설정 이름과 저장값을 맞춰 주세요

### 증강

| ML 필드 | 화면에서의 뜻 | 기본값 또는 처리 |
|---|---|---|
| num_samples_per_class | 종류별 추가 생성 수 | 10, 양수·상한 검증 필요 |
| strength | 원본 변화 강도 | 0.3, 범위 0~1 |
| finetune_steps | 생성기를 내 이미지에 맞추는 추가 학습 횟수 | null/생략 시 서버 설정, 코드 기본 400 |
| steps | 이미지 생성 계산 단계 수 | null/생략 시 서버 설정, 코드 기본 50 |
| seed | 무작위 계산의 시작값 | 선택한 값 기록 |
| normal_images_base64 / anomaly_images_base64 | 실제 정상·비정상 이미지 내용 | BE가 승인된 파일에서 구성 |

**null**은 값을 지정하지 않았다는 표현이다. 이 경우 실제 서버 기본값이 무엇이었는지도 기록해야 한다.

이전 `model_name`, `sampling_steps`, `guidance_scale`은 최신 증강 요청에서 제거됐다. 현재 ML은 모르는 필드를 무시할 수 있으므로 응답이 성공했다고 모든 설정이 적용된 것은 아니다.

BE의 RecipeRegisterRequest에는 modelName, sampler, cfgScale, resolution, batchSize 등 이전 생성기 설정이 남아 있고, AugmentationConfig에도 이전 필드가 남아 있다. 요청 DTO·레시피 저장·조회 응답·실행 변환을 함께 수정한다. 실제로 조절하지 않는 항목을 화면에서 선택 가능하게 표시하지 않는다.

### 학습

현재 ML은 `dataset_id`, `k_shot`, `epochs`, `q_query`, `episodes_per_epoch`, `seed`를 받는다. 각 항목의 뜻은 [프론트 안내의 학습 표](README.md)에 있다.

`query_images_base64`, `has_query_labels`는 제거됐다. Q-query는 저장된 데이터셋 안에서 연습용 이미지를 뽑는 수이며 별도 업로드 파일 수가 아니다.

### 작업에 남길 설정

사용자가 입력한 값과 서버 기본값을 합쳐 **최종 실제 설정**을 저장한다. 설정을 그때의 사본으로 남기는 것을 **스냅샷**이라고 한다. 원본 레시피가 나중에 바뀌어도 지난 작업이 어떤 설정으로 실행됐는지 알 수 있어야 한다. 모델/엔진 종류와 설정 형식의 버전도 기록한다.

## 5. 이미지 제한을 같이 정해 주세요

배포 문서의 종류별 최대 업로드 10장·최대 생성 100장은 현재 ML 요청 검증이 강제하지 않는다. 시험에서 11장/101장, 여러 0·음수 설정이 통과했다.

합의할 값:
- 종류별 최소·최대 입력 개수와 전체 입력 수.
- 장당 용량, 한 요청의 전체 용량, 최대 픽셀 크기.
- JPG/PNG 등 허용 형식과 손상된 이미지 처리.
- 생성 수·추가 학습·생성 단계의 상한.
- K-shot과 Q-query를 사용할 때 필요한 실제 데이터 수.
- 원본 비율 유지·잘라내기·128×128 변환 방식.

현재 BE 업로드는 장당 10MB, 한 요청 합계 50MB다. 10MB 이미지 20장을 한 번에 보내는 방식과 충돌한다. **multipart**는 파일을 전송하는 요청 형식이고, ML의 JSON/Base64 요청은 다른 형식이므로 용량 제한도 각각 검토한다.

FE는 선택 순간 빠르게 안내하고, BE·ML도 같은 규칙을 검증해야 한다.

## 6. 기다리는 작업과 결과를 연결해 주세요

BE 기록에 사용자·프로젝트·입력 파일·BE Job ID·ML job_id·데이터셋/모델 ID를 묶어 저장한다. **ID는 대상을 찾는 번호**다.

| ML 공개 상태 | 사용자에게 설명할 뜻 |
|---|---|
| PENDING | 계산 대기 중 |
| STARTED / RUNNING | 계산 진행 중 |
| SUCCESS | 성공, 실제 결과 확인 가능 |
| FAILED | 실패, 원인 안내 필요 |
| CANCELLED | 취소 상태 값은 정의돼 있으나 현재 취소 API는 없음 |

Celery 내부의 FAILURE를 ML 공개 API가 FAILED로 바꾼다. FE의 COMPLETED 같은 이름도 명시적으로 변환한다.

학습은 파일 저장 전에 progress=100이 나올 수 있다. 완료 판단은 퍼센트가 아니라 성공 상태와 결과를 기준으로 한다. 화면에는 회의 결정대로 %와 바를 빼고 상태를 표시한다.

Redis의 임시 기록만으로 영구 작업 목록을 대신하지 않는다. 새로고침 후에도 BE에 저장된 결과를 다시 볼 수 있어야 한다.

**멱등성**은 같은 요청을 여러 번 보내도 작업 생성·차감은 한 번만 하는 성질이다. 사용자가 두 번 클릭하거나 통신 실패로 재시도해도 GPU 작업과 개미 차감이 중복되지 않게 요청 식별자를 사용한다.

현재 ML 취소 API가 없으므로 FE에서 취소 성공처럼 표시하지 않는다. 오류는 사용자에게 이해할 설명과 개발자가 찾을 로그를 나눠 보관한다.

## 7. 파일과 용량은 실제 저장소와 맞춰 주세요

**S3**는 클라우드 파일 보관함, **로컬 경로**는 서버 디스크의 파일 위치다. 현재 S3 업로드 후 다음 학습·추론은 로컬에서 찾으므로 읽기 경로도 연결해야 한다.

파일 기록에는 소유자·프로젝트·Job·저장소 키·실제 크기·유형·생성 시각·다른 작업의 사용 관계를 담는다. **저장소 키**는 클라우드에서 파일을 찾는 이름이다. 만료되는 다운로드 URL 자체를 영구 식별자로 저장하지 않는다.

삭제 전에는 다른 작업이 파일을 쓰는지 확인한다. 예를 들어 증강 데이터를 학습이 사용 중이면 곧바로 삭제하면 안 된다. 실제 파일 삭제가 성공한 뒤 용량을 줄이고, 임시 업로드·로컬 복사본·실패 잔여물도 정리 기준을 정한다.

**쿼터(Quota)**는 허용 저장량이다. 사용자별인지 팀별인지 프로젝트별인지 아직 합의가 필요하다. 프로젝트 수 무제한 결정은 유지한다.

동시 실행을 고려해 작업 전에 예상 공간을 **예약**하고 완료 후 실제 바이트로 **정산**한다. 클라우드 전체 사용량만으로 사용자별 사용량을 알 수 없으므로 파일 기록과 실제 저장소를 주기적으로 대조한다.

## 8. 개미 정책은 기존 검수 코드와 함께 확인해 주세요

기존 검수 경로는 신청 시 포인트 차감, 승인 또는 거절 완료 시 전문가에게 보상의 90% 지급, 지급 이력 기록을 포함한다. 새 정책과 일치하는지 확인한다.

아직 합의할 것:
- Job 종류·생성 수·계산 횟수에 따른 가격과 가격표 버전.
- 실행 전 비용 안내, 잔액 예약, 실제 차감 시점.
- 시작 전 실패·실행 중 실패·취소의 환급 조건.
- 레시피 포크 비용과 증강 실행 비용의 구분.
- 전문가 답변·검수·포크 보상의 지급 조건과 중복 수령 방지.
- Toss 결제 검증과 개미 충전 연결.

증감 내역을 보관하는 기록을 **원장**이라고 한다. “왜 개미가 줄거나 늘었는가?”를 Job·결제·보상 사건과 연결해 설명할 수 있어야 한다.

가격은 이번 조사에서 책정하지 않았다. 저장 파일 삭제와 이미 사용한 GPU 계산 비용 환급은 별도다. 현금화·프로젝트 수 제한은 다시 추가하지 않는다.

## 9. 담당과 완료 기준

| 담당 | 먼저 할 일 |
|---|---|
| ML | 외부 코드·가중치 확보, 실제 GPU 실행, 입력 제한 검증 |
| BE | 실행 API, 파일 권한, 작업 상태·결과 저장 연결 |
| FE | 최신 입력 항목, 실제 이미지·결과 연결, 모의 성공 제거 |

포크 레시피 실행은 내 사본 → 프로젝트 선택 → 원본 선택 → 설정 수정 → 비용 확인 → 증강 생성 순서로 연결한다. 자세한 그림은 [설계도](ARCHITECTURE.md)에 있다.

회의에서 먼저 확정할 질문은 **모델 파일·외부 코드 버전, GPU 환경, 입력 제한, API 형식, 용량 소유 단위, 삭제·환급 조건**이다.

첫 완료 기준은 실제 이미지로 세 단계를 끝내고, 새로고침 후 같은 결과를 조회하며, 실제 실행값·파일·비용 기록이 서로 맞는 것이다.
