# RunPod 첫 실행·검증 안내

기준: 2026-10-12, BIFUSION-ML origin/Medfusion ffd687b, Bifusion_pip version-Med 3675ae6. 아직 RunPod에서 실행한 결과가 아니다. 아래는 코드 조사에 근거한 실행 계획이며, 실제 외부 Medfusion 코드와 가중치 파일을 확보한 다음 검증해야 한다.


## 이 문서를 읽는 방법

**목표는 작은 설정으로 증강 → 학습 → 추론을 한 번 이어서 실행하는 것이다.** 성공하면 연결이 된 것이고, 품질·속도 평가에는 별도의 시험이 필요하다.

### 먼저 알아둘 용어

| 용어 | 뜻과 이번 시험에서의 역할 |
|---|---|
| Pod | RunPod에서 빌리는 컴퓨터 실행 환경. GPU와 디스크를 갖는다 |
| GPU | AI의 많은 계산을 빠르게 수행하는 장치 |
| PyTorch / torch | 모델 계산을 수행하는 Python 도구 / 코드에서 쓰는 이름 |
| CUDA | PyTorch가 NVIDIA GPU를 사용하도록 연결하는 기술 |

| Diffusion | 잡음을 점차 줄여 이미지를 만드는 생성 방식 |

| /workspace | Pod에서 사용하는 디렉터리. 선택한 저장 유형에 따라 보존 조건이 다름 |

모델 코드만 있으면 계산 방법만 있는 상태다. 체크포인트를 확보해야 학습된 생성기를 사용할 수 있다.


## 1. 실행 전에 확보할 것

- ML 코드: [Medfusion 브랜치](https://github.com/NoDataNoLife/BIFUSION-ML/tree/Medfusion).
- pip 코드: [version-Med 브랜치](https://github.com/NoDataNoLife/Bifusion_pip/tree/version-Med). pip는 여기서 프로젝트의 Python 패키지 저장소를 뜻한다.
- 외부 medical_diffusion 코드의 정확한 버전. 공개 원본을 조사했지만 팀의 가중치와 맞는 버전이라고 확인된 것은 아니다.
- VAE와 Diffusion 체크포인트 2개. 체크포인트는 학습된 모델의 숫자들을 저장한 파일이다. 저장소 코드만 받아서는 실행할 수 없다.
- 실제 테스트 이미지, 사용 허용 여부, 클래스 의미. 포함된 bloodmnist_binary는 림프구/호중구 분류용이며 정상/비정상 데이터로 설명하면 안 된다.
- Pod 예상 사용시간, GPU와 저장장치 과금, 종료 책임자. 가격과 실제 속도는 이 조사로 확정하지 않았다.

ML의 DEPLOYMENT.md가 제안하는 RTX 5090을 사용한다면 Blackwell 지원 환경을 확인한다. PyTorch 2.7은 CUDA 12.8 휠을 통해 Blackwell 지원을 추가했다. torch와 torchvision의 호환 버전을 함께 맞추고, 단순 설치 성공이 아니라 실제 GPU 연산까지 시험한다. [PyTorch 공식 안내](https://pytorch.org/blog/pytorch-2-7/)

## 2. 첫 시험은 Pod 하나·GPU 작업자 하나로

**이 단계의 목표:** 한 GPU에 여러 계산이 겹쳐 메모리가 부족해지는 상황을 피한다. 대기 중인 작업은 먼저 시작한 계산이 끝난 뒤 실행된다.

추천하는 첫 구성:

```text
FE → BE(연동 구현 필요) → ML API
                            ↓ 작업 등록
                          Redis
                            ↓
                 Celery 작업자 1개 → GPU
                            ↓
                  /workspace의 결과 파일
```

Redis는 할 일을 보관하는 대기열, Celery 작업자는 대기열에서 일을 가져와 실행하는 프로그램이다. API가 요청을 받자마자 작업 ID를 돌려주고, 계산은 작업자가 따로 수행한다.

DEPLOYMENT.md의 증강·학습·추론 작업자를 각각 하나씩 띄우는 방식은 전체 작업이 한 개로 제한되는 구성이 아니다. GPU 작업 3개가 동시에 실행될 수 있다. 첫 시험에서는 아래처럼 세 종류 대기열을 작업자 하나가 처리하게 한다.

```bash
celery -A app.core.celery_app worker -Q augmentation,training,inference --pool=solo --concurrency=1 --prefetch-multiplier=1 --loglevel=info
```

명령에서 알아둘 부분:
- `-A app.core.celery_app`: ML 코드의 대기열 설정을 사용한다.
- `-Q augmentation,training,inference`: 증강·학습·추론 세 종류의 일을 모두 받는다.
- `--pool=solo --concurrency=1`: 이 작업자에서 계산을 하나씩 수행한다.
- `--prefetch-multiplier=1`: 다음 작업을 과도하게 미리 가져오지 않게 한다.
- `--loglevel=info`: 실행 상태를 터미널에 출력한다.

실행 전에 현재 소스의 Celery 애플리케이션 import 경로와 큐 이름을 다시 확인한다. Redis, API, 작업자는 각각 실행 상태를 유지해야 한다. 브라우저 터미널을 닫으면 함께 종료되는 실행 방식은 장기 운영용이 아니다.

## 3. 설치와 설정 순서

**이 단계의 목표:** 코드와 필요한 Python 도구를 같은 환경에서 실행하도록 맞춘다. 아래는 설치 계획이며, 팀의 모델 파일과 실제 Pod 환경에 맞는 설치 명령은 실행 시 확인해야 한다.

1. GPU PyTorch가 준비된 Pod 환경을 고르고 Python 버전을 기록한다. 프로젝트 배포 문서 기준은 Python 3.11이다.
2. /workspace 아래에 ML, pip, 외부 Medfusion 코드와 가중치를 둔다. 각 저장소 커밋과 가중치 SHA256을 기록한다. 커밋은 코드의 버전 기록이고, SHA256은 파일 내용이 같은지 확인하는 긴 식별값이다. 나중에 성공한 환경을 다시 만들기 위해 남긴다.
3. 프로젝트용 Python 가상환경을 만든다. 가상환경은 프로젝트마다 필요한 도구 버전을 따로 설치하는 공간이다. 기존 CUDA용 torch 설치를 CPU 버전으로 덮어쓰지 않도록 설치 결과를 확인한다.
4. ML requirements와 pip 패키지를 설치한다. requirements는 필요한 Python 도구 목록이다. 여기서 pip 패키지는 Bifusion_pip 저장소의 코드 묶음이며, 설치 명령 도구 pip와 구분한다. 외부 medical_diffusion을 실제로 import할 수 있게 설치/경로를 구성한다. 현재 의존성 버전이 충분히 고정돼 있지 않아 설치 명령만으로 성공을 보장할 수 없다.
5. python -m pip check로 패키지 충돌을 확인하고, 성공한 환경은 python -m pip freeze로 저장한다.
6. ML 저장소의 설정 클래스와 .env 예시를 대조해 GPU 장치, 두 체크포인트 경로, Redis 주소, 로컬 저장 위치를 지정한다. .env는 이런 실행 설정을 담는 파일이다. 첫 시험의 영구 결과 위치는 /workspace 아래로 통일한다.
7. ML 저장소를 작업 디렉터리로 사용한다. DEPLOYMENT.md의 grep/xargs로 .env를 export하는 명령은 공백과 주석에 취약하므로 그대로 복사하지 않는다. 애플리케이션의 dotenv 로딩을 사용한다.
8. Redis를 로컬에서 시작하고 외부에 6379 포트를 공개하지 않는다. 그다음 작업자 하나와 API를 실행한다.

API를 Pod 내부에서 먼저 확인할 때:

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

127.0.0.1은 같은 Pod 안에서만 접속할 주소이고 8000은 접속 포트 번호다. 위 uvicorn 명령은 계산 작업자가 아니라 요청을 접수하는 API 서버를 켠다.

위 명령들은 ML 저장소 디렉터리에서 해당 Python 환경을 활성화한 뒤 실행한다. 공개 접속은 인증을 추가한 뒤 구성한다. 현재 ML API 자체에는 호출자 인증이 없다.

외부 포트 공개에는 0.0.0.0 바인딩과 RunPod 포트 설정이 필요하다. HTTPS 프록시에는 100초 제한이 있으므로 GPU 계산 완료까지 POST 연결을 붙들고 있지 말고 작업 ID를 반환한 후 상태를 조회해야 한다. [RunPod 포트 공식 문서](https://docs.runpod.io/pods/configuration/expose-ports)

## 4. GPU 사전 확인

**이 단계의 목표:** GPU가 목록에 보이는 것에서 끝내지 않고, 실제 계산까지 가능한지 확인한다. 코드를 실행하면 PyTorch/CUDA 버전과 GPU 이름, 계산 결과 숫자가 출력돼야 한다.

같은 Python 환경에서 다음을 실행한다.

```python
import torch
assert torch.cuda.is_available(), "GPU 사용 불가"
print(torch.__version__, torch.version.cuda)
print(torch.cuda.get_device_name(0))
x = torch.randn(512, 512, device="cuda")
y = x @ x
torch.cuda.synchronize()
print(float(y.mean()))
```

여기까지 성공하면 GPU 계산을 사용할 수 있다. 이어서 모델 파일을 메모리에 읽어 오는 과정을 로딩이라고 한다. 그다음 실제 Medfusion 생성기를 로딩해 체크포인트 호환성을 확인한다. /health가 성공해도 체크포인트 로딩이나 GPU 실행 성공을 뜻하지 않는다.

**모델 담당자와 확인할 세부 항목:** 외부 파이프라인의 use_ema도 확인해야 한다. EMA는 여러 시점의 모델 값을 평균해 보관하는 방식이다. 처음 읽을 때는 이 구현을 이해하기보다, 실제 추가 학습한 모델로 생성하는지 확인해야 한다는 의미로 읽으면 된다. 조사한 공개 구현은 이 값이 참이면 별도로 보관된 평균 모델로 생성할 수 있다. pip는 noise_estimator를 미세조정하므로, 실제 체크포인트 설정에 따라 미세조정한 모델이 생성에 사용되는지 확인해야 한다. 현재 팀 환경에서 발생했다고 확정한 오류는 아니다.

## 5. 최소 연결 시험: 증강 → 학습 → 추론

이 시험은 비용을 적게 들여 데이터 전달을 확인하는 용도다. 모델 품질이나 속도 비교 결과로 발표하면 안 된다.

### 증강

POST는 작업 시작 요청, GET은 상태 조회다. 아래 JSON은 요청에 담을 값의 형식이다. 이 주소는 ML 서버용이고, FE가 BE에 요청할 주소는 별도 합의가 필요하다.

POST /augmentation/run에 보낼 실제 ML 형식:

```json
{
  "normal_images_base64": ["실제 이미지의 base64 문자열"],
  "anomaly_images_base64": ["실제 이미지의 base64 문자열"],
  "num_samples_per_class": 2,
  "strength": 0.3,
  "finetune_steps": 2,
  "steps": 5,
  "seed": 42
}
```

위 한 장짜리 배열은 형식을 보여주는 예시다. 첫 통합 시험에는 각 클래스 5장 정도를 준비한다. 두 문자열을 그대로 보내면 이미지가 아니므로 실패한다. 이미지 인코딩에는 저장소의 image_utils를 이용한다.

응답에서 받은 job_id는 계산 작업 번호다. {job_id} 자리에 실제 번호를 넣어 GET /augmentation/{job_id}를 조회한다. dataset_id는 생성된 자료 묶음을 찾는 번호이고, NPZ는 이미지와 종류를 저장한 파일 형식이다. SUCCESS일 때 결과의 dataset_id, NPZ 파일, 미리보기와 실제 생성 개수를 확인한다. FAILED이면 오류를 기록한다. 모르는 ID도 PENDING으로 보일 수 있으므로 무한 대기하지 않는다.

### 학습

증강 결과에서 받은 실제 dataset_id를 사용한다.

```json
{
  "dataset_id": "증강 결과의 dataset_id",
  "k_shot": 1,
  "q_query": 1,
  "epochs": 1,
  "episodes_per_epoch": 1,
  "seed": 42
}
```

POST /training/run → GET /training/{job_id}. 성공 시 model_id와 실제 모델 파일을 확인한다. 이 설정은 작은 연결 시험용이며 정상 품질 평가 설정이 아니다.

k_shot은 각 클래스의 기준으로 삼는 이미지 수, q_query는 학습 중 맞혀 보게 하는 클래스별 이미지 수, episode는 이 연습을 한 번 수행하는 단위다. q_query용 이미지를 FE가 따로 업로드하는 구조가 아니다.

### 추론

POST /inference/run에는 학습 결과의 model_id와 실제 입력 이미지 내용을 보낸다. 형식은 다음과 같다.

```json
{
  "model_id": "학습 결과의 model_id",
  "images_base64": ["실제 이미지의 base64 문자열"],
  "seed": 42
}
```

이 분류 경로에서는 sampling_steps나 batch_size를 바꿔도 화면에서 기대하는 생성 설정·분류 처리량 조절 기능으로 작동하지 않는다. GET /inference/{job_id}로 완료를 확인한다.

확인할 것:
- 입력 이미지 수와 예측 결과 수가 같은가?
- 정상/비정상 라벨이 실제 데이터의 의미와 일치하는가?
- 결과 새로고침 후에도 같은 작업 결과를 다시 볼 수 있는가?
- 실패가 성공 화면이나 가짜 진행률로 바뀌지 않는가?
- 결과 파일을 서버 안에서만 찾는 것이 아니라 권한 있는 사용자가 다운로드할 수 있는가?

타임아웃으로 클라이언트를 종료해도 GPU 작업이 취소되지는 않는다. 현재 취소 API가 없으므로 작업자 로그와 GPU 사용 상태를 확인한다.

## 6. 실제 설정으로 두 번째 시험

최소 시험 성공 뒤 팀과 합의한 finetune_steps, steps, 생성 수로 다시 실행한다. 문서에 있는 특정 GPU의 30~75초·약 4.5GB 주장은 이번 조사에서 재현하지 않았다.

각 작업에서 기록:
- GPU 종류, torch/CUDA 버전, 코드 버전, 가중치 해시.
- 입력 이미지 개수·원본 크기·바이트 수.
- 사용자가 요청한 설정과 서버가 실제 적용한 설정.
- 대기 시간, 모델 최초 로딩 시간, 순수 실행 시간.
- 최대 GPU 메모리, 생성 파일 총 용량, 성공/실패.
- 같은 seed로 실행했을 때 결과가 얼마나 일치하는지. 현재 학습 경로는 seed만으로 완전한 재현성을 보장하지 않는다.

## 7. 저장장치와 S3는 별도로 검증

**이 단계의 목표:** 계산이 성공한 뒤에도 다음 작업에서 결과를 읽을 수 있게 한다. 로컬은 Pod 디스크, S3는 클라우드 파일 보관함이다.

현재 local 모드는 서버 파일 경로를 반환해 브라우저 다운로드가 바로 되지 않는다. S3 모드는 업로드할 수 있지만, 다음 학습/추론 단계는 로컬 파일을 찾는다. 따라서 STORAGE_BACKEND만 S3로 바꾸면 전체 흐름이 완성되지 않는다.

첫 시험은 API와 작업자가 같은 /workspace 결과 디렉터리를 사용하게 한다. 운영 전에는 S3 결과를 읽는 학습/추론 경로와 파일 소유권·다운로드 URL 재발급을 구현해야 한다.

RunPod의 컨테이너 디스크, 볼륨 디스크, 네트워크 볼륨은 보존 조건이 다르다. 컨테이너 디스크는 중지/재시작 시 보존되지 않으며, 볼륨 디스크는 Pod 종료 시 삭제될 수 있다. 네트워크 볼륨은 Pod와 별개로 유지된다. /workspace라는 이름만 보고 영구 보존된다고 판단하지 말고 선택한 저장 유형을 확인한다. 저장 비용도 별도다. [RunPod 저장장치 공식 문서](https://docs.runpod.io/pods/storage/types)

## 8. 첫 테스트 완료 기준

- 세 작업이 실제 파일을 이어받아 끝까지 성공했다.
- 실패 사례가 명확한 오류로 표시된다.
- GPU 작업이 동시에 하나만 실행된다.
- 결과와 실제 설정이 저장되고 다시 조회된다.
- 공개 API는 인증으로 보호된다.
- 작업 결과 파일의 위치·용량·삭제 방법을 확인했다.
- Pod 중지/종료와 볼륨 보존·과금 상태를 사용자가 확인했다.

현재 확인 상태: 정적 코드 분석, 요청 모델 검증, 어댑터 전달 및 이미지 변환 시험 완료. GPU 실행, 실제 체크포인트 로딩, RunPod 성능·비용 측정은 미실시.
