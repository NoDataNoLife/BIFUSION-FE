## 3. 저장소별 실제 역할

```text
브라우저 FE
  → Spring BE: 권한, 프로젝트, 작업 기록, 비용, 파일 관리
    → BIFUSION-ML: FastAPI가 요청 접수, Redis/Celery가 계산 순서 관리
      ├ 증강: ML 어댑터 → pip MedfusionGenerator → 외부 medical_diffusion + 가중치
      ├ 학습: ML 자체 ProtoNetService
      └ 추론: ML 자체 ProtoNetService
```

워커는 계산을 수행하는 프로세스, 큐는 계산 순서를 기다리는 대기열이다. Redis는 여기서 대기열과 작업 결과를 보관한다. BE는 사용자가 보는 영구 작업 기록을 따로 관리해야 한다.

### 혼동하기 쉬운 pip 기능

- pip의 기본 augment는 feature 방식이다. 이미지 자체 대신 특징 숫자를 보간해 늘린다. 웹 Medfusion 증강과 다르다.
- pip의 Python augment(mode="medfusion")는 클래스별 무조건부/조건부 생성 경로를 호출한다. 원본은 클래스 구조 확인에 쓰이며 웹의 업로드별 파인튜닝 경로와 같지 않다.
- pip CLI의 --mode 선택지는 feature/ddpm이다. Medfusion 모드를 CLI에 넣으면 현재 선택지 검증에서 거절된다.
- 웹이 쓰는 경로는 **MedfusionGenerator.augment_with_finetune**이다. 클래스별 원본에 적응한 뒤 원본을 변형해 생성한다.
- pip의 NPZ는 images/labels 등, 웹 NPZ는 x/y/ids다. 그대로 서로 바꿔 넣을 수 없다.
- 웹 모델은 256차원 인코더와 저장된 prototypes를 사용한다. pip의 일반 모델·feature 모델은 구조와 체크포인트 키가 다르고 추론 시 support 폴더도 요구한다. 같은 best.pt 이름이라고 호환되는 모델이 아니다.
- pip README/CLI_GUIDE에는 이전 DDPM·feature 중심 설명이 많다. 웹 실행 기준은 최신 ML 요청 스키마와 실제 호출 코드다.

## 4. 프론트 파라미터를 이렇게 맞춰야 한다

### 증강

| 항목 | 최신 ML 실제 동작 | 프론트 조치 |
|---|---|---|
| 정상·비정상 원본 | 각 Base64 배열 필요 | 장수만 보내는 현재 요청 수정. 실제 파일 업로드 연결 |
| num_samples_per_class | 클래스당 추가 생성 수, 기본 10 | “추가 생성 수”로 표시. 원본 포함 총수와 구분 |
| strength | 기본 0.3, 스키마 0~1 | 원본을 얼마나 변화시킬지 설정. 우선 기본값 제공 |
| finetune_steps | null이면 서버 기본 400; 배포 문서 예시는 200 | 초기에는 고급 설정 또는 서버 고정값. 실제 적용값 기록 |
| steps | null이면 서버 기본 50 | 현재 sampling_steps를 최신 steps로 교체 |
| seed | 선택한 정수 또는 null | 재실행 설정에 저장. 완전 동일 결과 보장 문구는 피함 |
| guidance_scale | 증강 요청에서 제거됨 | 현재 화면 옵션 제거. strength로 숫자만 옮겨선 안 됨 |
| model_name | 증강 요청에서 제거됨 | 사용자 선택으로 노출하지 않음 |

strength는 원본에 넣는 잡음의 비율이다. 낮으면 원본에 가깝고 높으면 변화가 커질 수 있다. **0도 정확한 원본 복사 모드가 아니다.** pip는 최소 잡음 시점을 1로 제한하고 VAE로 압축·복원한다. steps 역시 낮은 strength에서는 내부적으로 실제 횟수가 줄 수 있어 “200이면 항상 200회”라고 단정하면 안 된다.

원본은 웹 워커에서 128×128로 줄어든 뒤 pip에서 내부 256×256으로 확대되어 처리되고, 결과는 다시 128×128이다. 원본의 미세 정보가 복원되는 것은 아니다. 비정사각 이미지도 현재 강제로 정사각형으로 바꾸므로, 비율 유지·크롭 정책을 팀에서 정해야 한다. FE 레시피의 해상도 선택을 자유롭게 보여주면 현재 모델과 어긋난다.

### 학습

| 항목 | 최신 ML 실제 동작 | 프론트 조치 |
|---|---|---|
| dataset_id | 이전 증강 결과가 가리키는 파일 | 실제 완료 데이터셋 목록 사용 |
| k_shot | 기본 5 | 1/3/5/10은 문서 선택지이며 코드 강제는 아님. BE/ML 검증 추가 |
| epochs | 기본 30 | 학습 반복 횟수. 적용값 저장 |
| q_query | 기본 5 | 내부 학습 사례의 클래스당 평가 이미지 수. 외부 파일 업로드가 아님 |
| episodes_per_epoch | 기본 10 | 한 epoch 안에서 구성할 학습 사례 수. 고급 설정으로 두거나 고정 |
| seed | 기본 42 | 데이터 추출 난수에 사용. 현재 torch 초기화까지 완전 고정되진 않음 |
| query_images_base64 / has_query_labels | 최신 스키마에서 제거 | 현재 query 필수 업로드·정답 포함 토글 제거 또는 별도 후속 평가 기능 |

K-shot은 클래스당 참고 이미지 수, epoch는 학습 반복 단위, episode는 참고/평가 자료를 뽑아 만든 학습 사례다. 요청의 seed만 같아도 모델 초기값과 GPU 계산 조건까지 항상 같아지는 것은 아니다.

데이터가 적을 때 ML 샘플러는 중복 추출해 support/query가 겹칠 수 있다. 원본에서 파생된 합성 이미지를 같은 묶음으로 분리하지도 않는다. 학습 점수는 제품의 임상 성능이 아니며, 원본/대상 단위로 분리한 별도 검증이 필요하다.

### 추론

실제 model_id와 images_base64가 필요하다. 출력은 NORMAL/ANOMALY, confidence와 클래스 확률이다. 파일명·정답·UMAP·참고 이미지·정확도를 자동 제공하지 않는다. batch_size/sampling_steps는 단독 생성 쪽 옵션이며 현재 분류 요청의 처리량 조절 기능으로 연결되지 않는다.

ML 분류는 입력 전체를 한 번에 텐서로 만든다. 따라서 추론 이미지 장수·픽셀 수·총 전송량 상한도 필요하다.

## 5. 이미지 제한·업로드 방식

### 현재 사실

- 새 DEPLOYMENT.md: 정상/비정상 각 최대 10장, 생성 각 최대 100장이라고 설명.
- 실제 ML: **장수 최대값·생성 수 양수·steps 양수 제한 없음.** 11장·101장·0·음수가 스키마를 통과함을 재현했다.
- FE: 정상/비정상 각각 최소 5장, 최대 장수 없음. image/* 선택만으로는 파일 유효성을 보장하지 못함.
- BE 일반 multipart 설정: 파일당 10MB, 요청당 50MB. ML JSON/Base64 본문 제한과는 별개다.
- 잘못된 이미지 문자열을 워커가 건너뛰므로 결과와 원본 파일 순서가 어긋날 수 있음.
- ML은 각 클래스의 유효 원본이 최소 1장 있어야 증강한다. 서비스의 최소 입력 수는 학습 데이터 요건까지 고려해 따로 합의해야 함.

### 초기 정책 제안 — 확정 정책 아님

증강 원본 각 1~10장, 추가 생성 각 1~100장을 상한 후보로 삼고 RunPod 실측으로 조정한다. 현재 FE 최소 5장은 합의 전 임의로 낮추지 않는다. 확장자는 PNG/JPEG부터 지원하고 장당 용량, 원본 최대 가로·세로/총 픽셀, 요청 전체 바이트를 함께 제한한다. DICOM·3D 영상·다중 프레임은 별도 지원 없이는 지원 대상으로 표시하지 않는다.

파일 수만 제한해도 고해상도 압축 이미지가 메모리를 많이 사용할 수 있다. 이미지 내용을 열어 확인하는 검증은 BE/ML에도 필요하다. 파일 선택 전에 FE가 빠르게 안내하고, 서버가 최종 검증한다.

### 업로드 권장 흐름

1. FE → BE의 파일 업로드(기존 /api/v1/files/temp 재사용 여부 검토).
2. BE가 파일 ID·소유자·크기·실제 이미지 형식을 확인하고 저장.
3. 작업 생성에는 normalFileIds/anomalyFileIds를 전달하는 계약을 제안.
4. BE가 승인된 파일을 읽어 ML이 받는 Base64로 변환하거나, 추후 ML에 저장소 키 입력 기능을 추가.
5. 작업에 연결한 파일은 임시 파일 정리 대상에서 제외하고 결과 파일도 작업과 연결.

현재 ML은 fileIds/S3 key를 직접 받지 않는다. 위 3~4단계는 추가 구현이다. 기존 파일 업로드도 이미지 전용 검사·프로젝트 연결·용량 제한·임시 파일 수명 규칙을 검토해야 한다.

Base64는 파일을 문자열로 바꾸는 방식으로 전송 크기가 원본의 대략 4/3로 늘어난다. 이미지 전체가 Celery의 JSON 작업에도 실리므로 많은 원본을 매번 큐에 넣는 구조는 장기적으로 피하는 편이 좋다. 20장×10MB를 한 요청으로 보내면 현재 BE 요청당 50MB와도 맞지 않는다. FE 업로드 묶음·서버 총량 제한을 함께 정해야 한다.

## 6. 실제 생성기의 동작에서 추가 확인한 점

- 입력 K장에 출력 N장을 요청하면 pip는 원본당 ceil(N/K)장을 만들고 웹 어댑터가 앞 N장만 반환한다. 입력 3장·출력 10장이면 12장 계산 후 10장 사용한다. 시간·비용은 반환 장수만으로 정확히 설명되지 않는다. 원본별 생성 수의 균형도 따로 확인해야 한다.
- 생성기 모델은 프로세스 안에 캐시되고, 업로드별 적응 학습 후 UNet 가중치를 finally에서 복원한다. 동일 프로세스에 여러 요청을 동시에 넣는 구조로 임의 변경하지 않는다.
- 원본 전체를 한 번에 VAE로 인코딩하는 부분이 있어 업로드 장수 상한은 메모리와 직접 관련된다.
- 외부 medical_diffusion의 코드와 가중치는 두 저장소에 포함돼 있지 않다. 팀의 실제 파일·출처·버전·해시가 필요하다.
- **조건부 확인사항:** 공식 Medfusion 참고 소스는 use_ema=True일 때 평균 모델로 생성하지만, pip 적응 학습은 일반 noise_estimator를 수정한다. 실제 가중치가 EMA를 쓰면 학습한 값이 생성에 적용되는지 확인해야 한다. 팀 가중치가 없어 발생을 확정할 수 없으며, 배포 전 pipe.use_ema와 생성 경로를 확인한다.
- 업로드 적응 학습이 다음 단계의 분류 모델 학습과 같은 일이 아니다. 전자는 생성기를 원본에 맞추는 작업, 후자는 분류기를 학습하는 작업이다.

### 샘플 데이터 주의

pip의 bloodmnist_binary/metadata.json은 class_0=lymphocyte(림프구), class_1=neutrophil(호중구)라고 명시한다. 정상/비정상 데이터셋이 아니다. 웹 출력 라벨이 NORMAL/ANOMALY라고 해서 두 세포 종류를 건강/질환으로 해석할 수 없다. 이 샘플은 우선 입출력·파일·실행 흐름 확인용으로 쓰고 의미상 성능 검증과 분리한다.

## 7. 회의 결정과 현재 화면의 차이

| 회의 결정 | 현재 화면/코드 | 조치 |
|---|---|---|
| 진행률 바 일단 제거 | 3개 진행 화면에 %와 바 유지 | 바·% 제거, 대기/실행/완료/실패와 재조회는 유지 |
| 프로젝트 무제한 | AI 실행·자원 정책 별도 정리 필요 | 요금제 설계에 프로젝트 수 제한 재도입하지 않기 |
| 저장 용량 고정 | 홈 35GB/100GB 고정값 | 실제 사용량/예약량/한도 API로 교체 |
| 작업별 개미 사용 | 실제 비용 예약·차감 연동 없음 | BE 예상 비용·잔액·정산 계약 필요 |
| 포크 레시피 → 프로젝트 → 증강 | 해당 실행 흐름 없음 | 프로젝트·원본 선택, 설정 검토/수정, 작업 생성 연결 |
| 나머지 화면 불일치는 후순위 | 예시 성능·품질·검수 표시 존재 | 추가 차트는 후순위, 오해를 주는 완료·점수 표시는 먼저 정리 |

진행률 바 제거는 “상태 조회 제거”가 아니다. 시작 요청 직후 끝나는 계산이 아니므로 새로고침·재접속에도 대기/실행/실패/완료를 알 수 있어야 한다.

레시피의 기존 modelName/sampler/cfgScale/resolution/batchSize는 최신 증강 API의 실제 조절항목과 다르다. 레시피 DTO/저장 구조에 strength, finetuneSteps, steps, 생성 수와 엔진 버전 등을 반영해야 한다. 모델명·샘플러·해상도·배치가 실제 고정이라면 수정 가능한 설정으로 보여주지 않는다. **“이대로 증강”도 원본 이미지가 필요하다.** 레시피가 설정만 담는지 데이터 접근 권한도 포함하는지 정해야 한다.

## 8. 개미·저장소·검수에 관해 BE에 요구할 것

- 개미는 서비스 내 사용 크레딧으로 정의하고, 회의에서 취소한 현금화는 범위에 넣지 않는다. ML은 결제·리워드를 계산하지 않는다.
- 작업 1건을 동일 가격으로 치기보다 생성 수·적응 반복 수·생성 반복 수·학습 규모에 따른 비용표를 검토한다. 다만 최종 가격은 GPU 실측 원가·운영비·정책 합의 후 정한다.
- 결제·충전, 전문가 검수, Q&A 답변, 포크 보상은 별개의 지급 사건이다. 중복 지급 방지와 지급/취소 시점을 정의한다.
- 기존 BE에는 검수 신청 시 포인트 차감, 승인/거절 완료 시 전문가 90% 지급 코드가 있다. “리워드 전부 미구현”은 아니다. 다만 이것이 새 개미 경제·Job 과금·Toss 충전까지 구현됐다는 의미도 아니다.
- 동일한 작업 재요청·콜백 재처리로 이중 차감하지 않도록 식별키와 원장(증감 내역)을 둔다.
- 고정 저장소 한도가 사용자 기준인지 프로젝트/팀 기준인지 먼저 확정한다. 프로젝트 무제한과 자원 무제한은 별개다.
- “Job 삭제 → 사용량 감소”는 실제 파일 삭제가 성공하고 다른 모델/레시피가 참조하지 않을 때 성립한다. 원본·NPZ·모델·미리보기·캐시·실패 잔여물을 어떻게 삭제할지 정해야 한다.
- 클라우드 전체 사용량 조회만으로 사용자별 사용량을 알 수 없다. 파일별 실제 bytes·소유자·Job 연결 기록과 정기 대조가 필요하다. 동시 요청을 위해 작업 시작 전에 용량을 예약한다.

## 9. 프로젝트 컨셉 제안

**“소량의 의료·생물학 이미지로 증강 실험을 만들고, 설정을 레시피로 공유·재사용하며, 전문가 검토와 후속 분류 실험까지 연결하는 협업 서비스.”**

현재 코드와 회의 방향을 바탕으로 한 제품 정의 제안이다. “모델이 진단을 정확히 해주는 서비스” 또는 “합성 이미지는 자동 검수된 고품질 데이터”라고 설명할 근거는 부족하다.

차별점 후보는 생성 모델 자체보다 **원본 기반 실험 → 설정/버전 기록 → 레시피 재사용 → 전문가 검토 → 분류 실험 비교**의 연결이다. 시장 전체 대비 독창성이 입증됐다는 뜻은 아니다. 시연에서는 원본 대비 어떤 실험을 했는지, 어떤 설정을 재사용했는지, 실제 전문가 의견이 무엇인지 보여주는 편이 코드와 맞는다.
